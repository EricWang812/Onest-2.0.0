# Decisions

Running log of judgment calls made while building Focus Lock autonomously, and everything that could not be implemented or verified in this environment. Newest entries at the bottom of each section as the build progresses.

## Environment constraints (checked at build start)

- No Docker, no Android SDK/`adb`/`gradle`, no macOS, on this Windows dev machine. Node v24.13.0 / npm 11 / Java 11 available.
- **Consequence:** relay logic is built and tested directly with `vitest` (not inside its Docker container — the Dockerfile/compose file are written but the image was never built here). Desktop Windows path is buildable/runnable here; desktop macOS path is real source, not compiled or run. Android is real Kotlin source, not compiled (`./gradlew assembleDebug` not run — no SDK). iOS is a design document per the user's own explicit fallback instruction.

## `/shared`

- **SQLite: `node:sqlite` instead of `better-sqlite3`.** Node 24 ships `node:sqlite` (confirmed working via `DatabaseSync`) with zero native-compile step. `better-sqlite3` needs a prebuilt binary for the exact Node ABI or a full native toolchain rebuild; on a very new Node version (24.13) that's a real risk of a broken `npm install` with no easy fallback here. `node:sqlite` gives the same relational guarantees for this project's needs. Logged as `ExperimentalWarning` at runtime — acceptable for a locally-run daemon/relay, not shipped to a browser.
- **Session-record signing: Node's built-in `crypto.sign`/`verify` with `ed25519`**, not a third-party crypto lib. Confirmed working. Zero extra dependency, well-tested by Node core.
- **Pairing PAKE: the `spake2` npm package (v1.0.2, symmetric SPAKE2, ED25519-SHA256-HKDF-HMAC-SCRYPT suite).** Its own README states verbatim: "This have not go through a formal cryptographic audit... Also this do not protect against time attacks as operations are probably not constant-time." I used it anyway rather than hand-rolling PAKE math (worse) or skipping the PAKE requirement (spec explicitly calls for SPAKE2 or equivalent, precisely so the pairing code alone is useless to an eavesdropper watching the relay). If this ships for real use beyond a demo, get this exchange reviewed or swap in a vetted implementation before trusting it against an active adversary. The relay never sees the code or derives the session key — it only routes two opaque protocol messages — so a compromised relay alone cannot break pairing even with this library's weaknesses; what's at risk is an attacker who can also observe/tamper with the exchange in real time.
- **"Group key" interpretation.** The spec says "the first device... generates... a signing keypair" (singular) and separately describes a `devices` table with a per-row `pubkey` column, which is ambiguous about whether each device has its own key or shares one. I implemented a single shared Ed25519 keypair per group, transported to each joining device (private key included) over the SPAKE2-derived AES-128-GCM channel. Every device signs with the same key; every device verifies against the same public key. `devices.pubkey` stores that shared public key per row (redundant across rows) rather than a per-device key. Rationale: the group itself, not the individual device, is this system's trust boundary (no accounts, no per-device revocation model was specified), and a single shared key is simpler to verify against. Documented here because a per-device-key model is an equally valid reading and a reasonable future hardening if device-level revocation is ever wanted.
- **AES-128-GCM, not AES-256-GCM, for the group-key transport.** The SPAKE2 library's derived Ke (encryption key half of the transcript hash) is 16 bytes (half of a SHA-256 digest), not 32 — so AES-256-GCM isn't an option without an extra KDF step I chose not to add. AES-128-GCM with a 16-byte key from a fresh-per-pairing SPAKE2 transcript is not the weak link here.
- **Pairing identity strings are fixed constants** (focuslock-host / focuslock-joiner), not per-device IDs, since the host doesn't know the joiner's device ID before the exchange completes.

## `/relay`

- **`node:sqlite` is imported via `createRequire`, not a static `import`.** Vite/vitest's built-in-module allowlist (as of the installed Vite 5.4.21) predates `node:sqlite` (Node 22.5+), so a static `import { DatabaseSync } from 'node:sqlite'` gets misresolved as an attempt to load an npm package literally named `sqlite`, and the test run fails immediately. `createRequire(import.meta.url)('node:sqlite')` isn't statically analyzed by Vite's import scanner, so it passes through untouched in both `tsc` and `vitest`. A type-only `import type { DatabaseSync }` is used separately for typechecking (erased at compile time, so it doesn't trigger the runtime issue).
- **Pairing is a blind relay.** `relay/src/server.ts` never imports `spake2` or does any PAKE math — it only looks up a challenge by its 6-digit code and forwards opaque `pairing.spake2_msg`/`pairing.group_key` payloads between the two sockets that share a `challenge_id`. This was a deliberate protocol design (not in the original spec's literal message list, which only sketched the record shape) so a compromised relay operator gains nothing beyond metadata (that a pairing happened) — it never sees the code, the derived key, or the group's private key.
- **Group signing key is registered on the relay from the first `hello` that includes a `pubkey`, idempotently (first-write-wins).** The relay needs the group's *public* key to verify `session.publish` signatures, but nothing in the spec's WS message list said how it learns it. There's no revocation or update path for this in the current implementation — a determined attacker who can inject a `hello` before the legitimate first device connects could squat a group's pubkey. Given the whole system has no accounts and trusts pairing-code possession as the security boundary, this is consistent with the rest of the design but is worth hardening (e.g., bind the first pubkey to the challenge that created the group) if this goes beyond a personal-use tool.
- **Found and fixed a real race condition, not just a test bug, while writing the pairing integration test.** The server sends `pairing.group_key` immediately followed by `pairing.complete` with no I/O gap between them (same synchronous handler, back-to-back `ws.send()` calls). On the wire these can arrive in the same socket read and get delivered as two synchronous `'message'` events before client code has a chance to `await`-then-register a fresh one-shot listener for the second message — silently dropping it. The integration test now uses a persistent listener that feeds a queue (`relay/test/relay.test.ts`), and **the same pattern must be used in every real client's relay-connection code** (desktop daemon, and by extension any future mobile client) — never a one-shot listener per pending request. Documented here so this isn't rediscovered the hard way on a device that then looks "stuck".
- Relay integration tests run directly against `buildServer()` over a real loopback WebSocket + a temp-file SQLite DB (not inside the Docker container, which was never built here — see environment constraints above). All 6 tests pass: full pairing handshake + group-key transport, wrong-code rejection, broadcast + reconnect-reconciliation, invalid-signature rejection, unregistered-group rejection, and the 8-hour cap rejection.

## `/desktop`

- **Architecture split: daemon (elevated, owns everything) / watchdog (elevated, heartbeat-only) / shell (non-elevated Electron, UI + popups + tray).** The spec's "renderer must be able to crash without affecting the session" requirement means the timer/enforcement logic cannot live in an Electron renderer *or* in Electron's main process, since a `BrowserWindow`-hosting process is exactly the kind of thing a user can fully quit from a tray menu. So the daemon is a plain Node process with no Electron/GUI dependency at all, run elevated as a service; Electron is only used for the optional UI shell, which talks to the daemon over the same IPC channel a CLI tool could use. Enforcement, the clock, the DB, and the relay connection all keep running with zero Electron process alive.
- **`SessionRecord.ends_at` is wall-clock (shared across devices via the relay) but the live daemon does not trust `Date.now()` for the "is this session over" decision.** `desktop/src/daemon/clock.ts`'s `SessionClock` anchors to `process.hrtime.bigint()` at session start and computes remaining time from monotonic elapsed time, so a user setting the system clock forward mid-session cannot end it early (verified in `desktop/test/clock.test.ts` by stubbing both `Date.now` and `process.hrtime.bigint`). This protection is necessarily scoped to one process lifetime — there's no monotonic reference across a restart, so a fresh process falls back to the plain wall-clock dead-man's-switch comparison in `shared/src/deadman.ts`. A clock rolled forward *across* a daemon kill/respawn is therefore not defended against; treated as an accepted gap given the time available, and notably the opposite direction (clock rolled back) is already handled correctly by the dead-man's switch's `ends_at` check.
- **Notifications are fired directly by the daemon via `node-notifier`, independent of whether the Electron shell is even running.** Only the custom-styled blocked-app *popup* window depends on the shell process being alive (it needs a real window). This means quitting the shell from its tray icon loses the popup visuals but not the enforcement, the session-complete toast, or the audit log — a deliberate, documented boundary the spec didn't explicitly draw.
- **IPC clients must dispatch by request `id`, never by "read the next line and assume it's my response."** Found via the real process-integration test (`desktop/test/daemon-process.test.ts`): `SessionManager.startSession()` broadcasts a `session.state` event to every connected IPC socket *before* its own IPC handler returns, so the RPC response for `start_session` can arrive on the wire *after* an unrelated broadcast on the same connection. A naive "first line = my answer" test client misread the broadcast as the response and the test failed even though the daemon behaved correctly. Fixed the test to parse every line and match on `id`, ignoring `{type:'event'}` frames — and this is the exact pattern `desktop/src/shell/ipc-client.ts` uses for the real Electron shell, for the same reason (mirrors the relay-client persistent-listener fix above).
- **Found and fixed a real watchdog/daemon spawn-storm, not just a test artifact, via the same integration test.** Two bugs compounded: (1) a fresh process's very first staleness check could fire before the process it just spawned had written its own first heartbeat, reading "no heartbeat file" as "stale" and spawning a redundant second instance — fixed by having the spawning side write an optimistic placeholder heartbeat for the child immediately after `spawn()`, in both `desktop/src/daemon/index.ts` and `desktop/src/watchdog/index.ts`. (2) More importantly: **the daemon unconditionally spawned a new watchdog on every startup**, including a watchdog-triggered respawn after a kill — where a live watchdog already exists, since it was the one that just detected the daemon was gone and restarted it. Every kill/respawn cycle was silently accumulating an extra orphaned watchdog process. Fixed by gating the daemon's spawn behind `isStale('watchdog')`, matching what the watchdog side already did correctly for daemon respawns. Caught by watching real process counts in Task Manager–equivalent (`Get-CimInstance Win32_Process`) after a test run, not by the test's own assertions — the assertions passed even with the leak. Worth remembering: passing tests don't prove the absence of resource leaks; check the actual process table too.
- **macOS enforcement gap (written, never run — no macOS available in this environment).** Windows uses the Windows Filtering Platform via `netsh advfirewall` for the DoH-resolver IP block and `tasklist`/`taskkill` for process enforcement, both of which work for a same-user elevated service without additional prompts. macOS's closest equivalents are `pf` anchors (coarser-grained, more fragile across OS updates, and increasingly constrained by System Integrity Protection even for root) and `ps`/`pkill` (constrained by TCC — killing another app's process from a background daemon can require an additional user-granted permission on modern macOS that a plain launchd daemon cannot self-grant). `desktop/src/daemon/enforcement-macos.ts` implements the closest real equivalent to each Windows mechanism, but it should be assumed weaker until verified on real hardware — this is exactly the kind of gap the spec asked to be written down rather than silently shipped as if equivalent.
- Desktop unit + integration tests: 20/20 passing — `SessionClock` monotonic-time behavior (including the clock-jump case), `DesktopDb` CRUD and log-range aggregation, `SessionManager`'s full lifecycle (8h cap rejection, double-start rejection, start→apply→publish, unblock-then-log-then-notify ordering, relay-outage-does-not-affect-enforcement, remote-session-start with signature verification, dead-man's-switch on startup for both expired and live rows), and the real spawned-process test above (session start writes an actual hosts-file block; SIGKILLing the daemon leaves the block untouched and the watchdog respawns it, confirmed via the daemon's heartbeat file advancing again within the test's bound).
- **Pairing crypto lives in the daemon, not the Electron renderer or main process.** `desktop/src/daemon/pairing-manager.ts` runs the SPAKE2 state machine (via `shared/src/pairing.ts`) because the daemon already owns the device's signing keypair and the relay connection; the renderer's `contextIsolation: true` + `nodeIntegration: false` settings mean it has no `node:crypto`/`Buffer` access anyway, so it could not have done this even as a convenience. The UI only ever sees `{code, expiresAt}` to render and a coarse `pairing.status` stream.
- **Pairing completion triggers a deliberate daemon self-restart** (`process.exit(0)`, picked up by the watchdog within ~2s) on the joining device, rather than hot-swapping the live `RelayClient`/`SessionManager` identity in place. The daemon's identity (device keypair, group_id) is set once at construction from whatever was on disk at boot; after a successful pairing the joiner's disk state changes (it adopts the host's shared group key), so the simplest correct way to make the running process reflect that is to let it restart and re-read its own bootstrap logic — reusing crash-recovery machinery that already has to exist and be correct, instead of adding a second, parallel "swap identity live" code path. Safe because no session can be active on a device that's still mid-pairing.
- **IPC command surface changed shape once implemented for real.** The original placeholder `pairing_spake2_msg`/`pairing_group_key` passthrough commands (raw relay-message forwarders) were removed once `PairingManager` existed to own that state machine internally — the UI never needed to see individual SPAKE2 messages, only `pairing_host_start`, `pairing_joiner_start`, and a `pairing.status` event stream. Removing them (rather than leaving unused dead passthroughs) kept the IPC surface honest about what a compromised or buggy renderer could actually reach.
- **Real launch verification, not just compilation.** Beyond `tsc`/`vitest`, this environment can actually run a Windows Electron app: `npm run build` → `electron .` was launched against a live dev-mode daemon and ran cleanly for the test window (Chromium's routine `network_service_instance_impl`/`gpu_process_host` log lines only, no renderer or main-process exceptions); the same was repeated against the electron-builder-packaged `release/win-unpacked/FocusLock.exe` with the same result. A full interactive click-through with screenshots was not done — no GUI-automation tooling was available for a native Electron window in this session — so treat the UI's *visual* correctness as un-verified even though its process lifecycle and IPC wiring are.
- **Follow-up #2: the user actually ran the installer, and it crashed on first launch — a real bug this session's smoke tests missed.** `C:\Program Files\FocusLock\FocusLock.exe` threw `Uncaught Exception: Error [ERR_MODULE_NOT_FOUND]: Cannot find module '...\resources\app.asar\dist\daemon\paths.js' imported from '...\resources\app.asar\dist\shell\main.js'` immediately at startup. Root cause: `shell/main.ts` imports `ipcEndpoint`/`ipcEndpointDev` from `daemon/paths.ts` across the shell/daemon boundary, but `electron-builder.yml`'s `files:` list only ever packaged `dist/shell/**/*` into `app.asar` — `dist/daemon` was never part of the asar (it ships separately as `extraResources/daemon.bundle.js`, a different, unrelated path). Since Node resolves all ESM imports before executing any of a module's code, this meant the *entire* main process failed at the very first line, before `app.whenReady()` ever ran — no window, no error dialog reliably visible in a short-lived automated check, nothing. **This is exactly why the earlier "smoke tested, ran cleanly" claims in this file weren't sufficient**: a `timeout 8s ./FocusLock.exe` check that only looks for the absence of Chromium's routine GPU/network-service log noise doesn't distinguish "the app is running" from "the main process died instantly and Chromium's browser-process-level subprocesses (GPU, network, crashpad) spun up anyway before JS ever ran" — both look identical to that check. Fixed by adding `dist/daemon/paths.js` specifically (confirmed via `@electron/asar list` to now be present in the packaged archive) to `files:`, and re-verified properly this time: not just "no crash in N seconds" but `Get-Process FocusLock | Select MainWindowTitle` showing an actual `"Focus Lock"`-titled window while the process was live. Grepped the rest of `desktop/src/shell/**` for the same cross-boundary import pattern — this was the only instance. The installer was recompiled with the fix (`FocusLock-Setup.exe`, same filename, contents changed); the *original* file handed to the user was broken, and the replacement has not yet been re-run through an actual elevated install by the user — only the packaged app's window-rendering was re-verified, not the full installer flow.
- **Follow-up #4: `/plan`-gated live UI audit (real CDP-driven clicks, not a code read) found four real functional bugs, all fixed.** Requested via `/ecc:plan` ("test all buttons... check functionality"); plan confirmed, then executed by launching the actual app with `--remote-debugging-port` and driving real clicks over the Chrome DevTools Protocol (Electron is Chromium underneath — no automation framework needed, ~150 lines of raw WebSocket JSON-RPC against `Runtime.evaluate`), once with no daemon running and once against a real local daemon+relay pair. Findings, all confirmed via the live pass and re-verified after fixing (not just reasoned about): **(1)** `Devices.tsx` gated its entire pairing-status UI on `pairing !== null`, which is never set when the very first IPC call fails (no daemon) — clicking "Pair new device" produced a byte-identical DOM before and after, i.e. zero visible feedback on a real failure. Fixed by gating on `status` instead. **(2)** `pairing-manager.ts` sends the host's first SPAKE2 message the instant the relay assigns a `challenge_id` — before any joiner has entered the code, guaranteed to hit the relay's correct-and-expected "peer not connected" response, which was being broadcast to the UI as a hard `pairing.status: error`. Live-observed: a freshly generated, still-valid pairing code flashed "Pairing failed" within about a second of every single attempt. Fixed by treating that one specific reason as expected/silent rather than fatal. **(3)** `App.tsx`'s "Daemon connected/disconnected" indicator relied solely on a one-shot `daemon:connected` event forwarded from the main process's `IpcClient`, which frequently fires before the renderer has finished mounting and registering its listener (the daemon connects the instant the window is created; React mount + effect registration takes longer) — live-observed running an actual real session while the sidebar still said "Daemon disconnected" the entire time. Fixed by also trusting a successful `getState()` round-trip as proof of connection. **(4)** `Settings.tsx`'s three save paths (categories, theme, relay URL) never checked whether `setSetting` actually succeeded, optimistically updating local UI state regardless — a save with no daemon connected looked identical to a real one. Fixed with a shared `trySave` helper that surfaces `res.error` in a visible banner. The full 47-test backend suite still passes after all four fixes. **Not done, and stated as a deliberate scope cut given cost pressure mid-session:** the plan's Task 4 (screenshot-based "best use of space" layout review across window sizes) — the functional pass surfaced real, higher-value bugs first and this was cut to close out efficiently rather than pursued for completeness. If picked up later, the CDP harness already exists as a proven pattern (`Page.captureScreenshot`) — it was simply not re-built after the scratch scripts were deleted post-audit.
- **Follow-up #5: the confirmed prediction — "the installer's own elevated flow was never run end-to-end" (Follow-up #1) — turned out to hide a real, serious bug, found only once the user actually ran it.** All three services installed (confirmed via `Get-WinEvent`, event ID 7045) but showed `Stopped` (`Get-Service`), and the Service Control Manager log recorded, for every one, three times across repeated attempts: `The service did not respond to the start or control request in a timely fashion` / `A timeout was reached (30000 milliseconds) while waiting for the ... service to connect` (event IDs 7000/7009). **Root cause: `sc.exe create` pointed directly at `node.exe daemon.bundle.js` creates a service *registry entry* fine, but a bare Node process has no idea it's running as a Windows Service and never performs the required Service Control Manager start handshake (the Win32 `StartServiceCtrlDispatcher`/`SetServiceStatus` protocol)** — so SCM waits the full 30s timeout and marks the service failed, regardless of whether the daemon's own logic is correct (and it was — this is exactly why every dev/test run in this session, which always ran the bundles as plain foreground processes, never caught it: that's a fundamentally different question from "does this behave as an actual Windows Service," and nothing short of an actual elevated service-start attempt on a real machine could have surfaced it). Fixed with [NSSM](https://nssm.cc) (`desktop/build/tools/nssm.exe`, downloaded directly from `nssm.cc/release/nssm-2.24.zip` since Chocolatey's own install is blocked here for the same permissions reason documented below) — a small, widely-used native shim that *does* speak the real SCM protocol on a wrapped process's behalf; this is the standard fix for running arbitrary executables (Node scripts, in particular) as Windows Services, not a workaround specific to this project. `focuslock.iss` now: (1) unconditionally `sc.exe stop`/`delete`s any same-named services first (a prior broken install, or the earlier build, would otherwise collide — Windows refuses to create a service whose name is taken), (2) uses `nssm install`/`set`/`start` for all three services, (3) sets `AppEnvironmentExtra` for cross-service env vars (replacing the earlier `reg.exe add ...\Environment` approach — NSSM does this natively) and `AppStdout`/`AppStderr` log redirection to `{app}\data\<ServiceName>.{stdout,stderr}.log`, a real diagnostic capability that didn't exist before (raw `sc.exe`-launched services had no log output anywhere). **Re-verified how far this environment can verify it**: `nssm.exe` confirmed as a genuine PE32+ Windows executable, the installer recompiled cleanly with it bundled — but the actual "services now report Running and the app connects" outcome depends on the user re-running the installer, since this session still cannot click through a live elevated install. If this recurs, `{app}\data\FocusLockDaemon.stderr.log` now exists specifically to make the next failure mode visible without needing the Event Log.
- **Follow-up #1: a real single-file installer was produced anyway, via Inno Setup instead of NSIS.** The NSIS blocker below is a permission boundary specific to electron-builder's toolchain (it needs `winCodeSign`, which needs symlink privilege), not to installer-building in general. Routed around it: `npx electron-builder --win dir` packages the app without ever touching `winCodeSign` (confirmed — that download only ever starts *after* `dir`-target packaging has already finished writing `release/win-unpacked/`, so killing the stuck retry loop afterward loses nothing). Chocolatey (`choco install innosetup`) also failed here, for the same root cause in a different spot — it needs to write to `C:\ProgramData\chocolatey\lib-bad`, which this session can't. Worked around by downloading Inno Setup's own installer directly from `files.jrsoftware.org` and running it `/VERYSILENT /DIR=` into a user-writable folder (`%LOCALAPPDATA%\InnoSetup`) instead of the default Program-Files-requiring location. `desktop/build/focuslock.iss` then wraps `release/win-unpacked/` into one `FocusLock-Setup.exe` (~86MB) that installs the UI plus three Windows Services — `FocusLockRelay`, `FocusLockDaemon`, `FocusLockWatchdog` — pre-wired to each other on `localhost` via per-service `Environment` registry values (`sc.exe` doesn't let a service inherit the installer's own process environment, so this has to go through `reg.exe add ...\Environment /t REG_MULTI_SZ`). Compiled successfully; the resulting `.exe` was smoke-tested by launching the unelevated `FocusLock.exe` inside the packaged output (ran cleanly), but **the installer's own elevated install flow (UAC prompt → service registration → three services actually starting) was not run end-to-end** — that requires clicking through a UAC prompt, which no automated tool in this session can do; only the user running it can complete that step. Required a second build change to make this possible at all: `desktop/build/build-node-bundles.mjs` (new) uses esbuild to compile the daemon/watchdog/relay into single self-contained `.bundle.js` files (all `node_modules` deps inlined) — without this, the services would have needed a full `node_modules` tree shipped alongside them, and `sc.exe`-launched services with no working directory context reliably fail to resolve bare `require()`s. Building these bundles surfaced two more esbuild/Node interop bugs, both fixed: esbuild's ESM-output `require()` shim for bundled CJS dependencies (`spake2` and friends) doesn't know about *any* Node builtin, prefixed or not, and throws "Dynamic require not supported" regardless of the `external` list — CJS output sidesteps this since real `require()` just works; and CJS output leaves `import.meta.url` empty, breaking the `createRequire(import.meta.url)('node:sqlite')` pattern used throughout this project, fixed via esbuild's documented `define`/`banner` recipe (substitute `import.meta.url` for a value computed from CJS's native `__filename` global). The daemon/watchdog's mutual respawn `WATCHDOG_ENTRY`/`DAEMON_ENTRY` path constants also needed `FOCUSLOCK_WATCHDOG_ENTRY`/`FOCUSLOCK_DAEMON_ENTRY` env-var overrides added, since the bundled files are flat siblings (`resources\daemon.bundle.js`), not the `dist/{daemon,watchdog}/index.js` subfolder pair the original relative-path logic assumed — all 20 desktop tests still pass with this change (the overrides are unset, and therefore inert, in every test).
- **Follow-up #3: the fixed installer still only showed a blank gradient — a second, more interesting bug in the same family.** The `dist/daemon/paths.js` fix (Follow-up #2) got the main process past its crash, but the user's next report was a rendered window with nothing in it but the CSS gradient background. Diagnosed properly this time — added temporary `webContents.on('console-message'|'did-fail-load'|'render-process-gone', ...)` forwarding in `main.ts` so the packaged app's renderer errors surface in the main process's own log (a packaged Electron app has no visible DevTools by default, which is exactly why this was invisible before), then launched with output captured. Root cause: **Electron's preload-script loader is not Node's module loader** — it does not honor `package.json`'s `"type": "module"` and cannot execute a bare `import` statement at all, under any configuration used here. `preload.ts` was being compiled by plain `tsc` (ESM output, since the whole `desktop` package is `"type": "module"`, needed elsewhere for `import.meta.url`), and failed to load with `SyntaxError: Cannot use import statement outside a module`. With no preload script, `contextBridge.exposeInMainWorld` never ran, so `window.focusLock` was `undefined` in the renderer; `api.ts`'s top-level `export const api = window.focusLock` silently captured that `undefined`; and the first real call (`App.tsx`'s `useEffect` calling `api.getState()`) threw `Cannot read properties of undefined (reading 'getState')`, which React's lack of an error boundary turned into "unmount everything, render nothing" — hence a page with only the `<body>` CSS gradient and zero DOM content. Fixed in `desktop/build/build-renderer.mjs`: `preload.ts` is now esbuild-bundled separately (`platform: 'node', format: 'cjs', external: ['electron']`) and overwrites `tsc`'s broken output at the same `dist/shell/preload.js` path, since `build:renderer` runs after `build:shell` in the `build` script. Verified properly this time, not just "no crash in N seconds": launched both the dev build and the repackaged `release/win-unpacked/FocusLock.exe` with the new console forwarding active, and confirmed the *only* renderer log line is React's routine "download React DevTools" dev-mode banner — which only prints once React's reconciler is actually running — with no errors of any kind. The installer was recompiled again with this fix. **Lesson for future debugging of this app specifically**: the `console-message`/`did-fail-load`/`render-process-gone` forwarding added to `main.ts` is a real, permanent diagnostic aid now (not reverted) — any future "looks wrong but nothing crashes visibly" report should start by reading the daemon/app's own stdout log, since renderer errors now flow there.
- **NSIS installer: packaging succeeds, final signed artifact does not, in this environment specifically.** `electron-builder --win` correctly packages the app (`release/win-unpacked/FocusLock.exe`, ~180MB, launches cleanly) and copies `daemon/`, `watchdog/`, and `shared/` into `resources/` exactly as configured in `electron-builder.yml`. The NSIS packaging step itself, however, unconditionally needs to extract a `winCodeSign` tools archive that contains symlinks (`darwin/10.12/lib/*.dylib`, unused by the Windows target but bundled in the same archive electron-builder ships), and creating a symlink on Windows requires either `SeCreateSymbolicLinkPrivilege` (granted to admins, or to any user once "Developer Mode" is turned on) or running elevated. `whoami /priv` in this session shows the privilege isn't present at all, and turning on Developer Mode itself requires the same admin rights this environment doesn't have. This is a Windows permission boundary, not a bug in `installer.nsh` or `electron-builder.yml` — **on a machine with Developer Mode enabled or run as Administrator, `npm run dist:win` should proceed to produce `FocusLock-Setup-<version>.exe`.** Not independently verified beyond that reasoning, since no such machine was available here.
- `installer.nsh`'s `sc.exe`-based service registration resolves `node.exe` via `where` on PATH at install time and requires a pre-existing Node.js 22+ install on the target machine (documented in README.md) rather than bundling a portable Node runtime as an installer resource — the latter is the more correct production approach (works with zero prerequisites) but wasn't done here given the time budget for a from-scratch build. The `installer.nsh` script itself was never executed (blocked by the same NSIS-stage limitation above), so its exact macro-hook behavior against electron-builder's NSIS template is unverified beyond following the documented `customInstall`/`customUnInstall` convention.

## `/android`

**Nothing in this section was compiled, let alone run.** This environment has no Android SDK, no `adb`, no emulator, and no physical device — confirmed at build start (`ANDROID_HOME`/`ANDROID_SDK_ROOT` unset, no SDK directory present). `./gradlew assembleDebug` was not executed. Every item below is a design/implementation decision made while writing real Kotlin source against the spec, not a verified fact about how that source behaves.

- **SPAKE2 pairing is NOT implemented on Android.** This is the single biggest functional gap in the whole project. Implementing the actual SPAKE2 elliptic-curve PAKE math by hand in Kotlin, in the time available, without any way to test it, was assessed as more dangerous than valuable — a silently-broken hand-rolled PAKE is worse than an honest gap, especially for something whose entire purpose is resisting an eavesdropper. `ui/DevicesTab` in `MainActivity.kt` has the intended UI (code display / code entry) wired up but calls no crypto — it's explicitly labeled "not implemented" in the UI copy itself, not silently stubbed. To close this gap: either port `shared/src/pairing.ts`'s use of the `spake2` npm package's math to Kotlin by hand (meaningful cryptographic engineering effort, needs review), or find and vet a maintained JVM/Android SPAKE2 library (none was identified/verified during this build). Everything downstream of pairing that doesn't strictly require it — session start/enforcement/logging/relay sync once a device already has a group identity — is implemented for real.
- **Ed25519 signing + AES-128-GCM (`crypto/CryptoUtils.kt`) use BouncyCastle's lightweight API**, not `java.security.Signature`/`javax.crypto`, specifically because Android's own Ed25519 support only became reliably available around API 33 — using it directly would silently misbehave or throw on minSdk 26–32 devices, a huge fraction of real Android installs. BouncyCastle's pure-JVM implementation behaves identically across the whole minSdk range. The canonical-JSON serialization in the same file was hand-written to match `shared/src/crypto.ts`'s `canonicalize()` byte-for-byte (sorted keys, no whitespace) since a signature only verifies if both sides hash the exact same bytes — **this cross-language byte-for-byte equivalence was reasoned through, not tested against the real Node implementation**, since doing so would require running the Kotlin code, which this environment cannot do.
- **The blocklist (`blocklist/Blocklist.kt`) is a hand-ported mirror of `shared/src/blocklist.ts`**, not a shared source of truth — Kotlin can't import a TypeScript module. This is a real, ongoing maintenance liability the spec's "single source of truth" language explicitly wanted avoided; a follow-up worth doing is generating both from one JSON file (which the daemon already validates and hashes at load — `shared/src/blocklist.ts`'s `blocklistHash()` — so a future step could have Android verify its mirror's hash against the daemon's over the relay and flag drift, rather than trusting the hand-port forever).
- **Domain blocking is a local-only DNS-interception `VpnService`** (`vpn/FocusLockVpnService.kt`): it becomes the device's DNS server (`addDnsServer`) but only routes traffic to that one fake DNS IP through the tunnel (`addRoute(fakeDnsIp, /32)`, not `0.0.0.0/0`), so it never sees or proxies general app traffic — matching the spec's explicit "do not route traffic anywhere external, the VPN terminates locally." Blocked queries get a synthetic 0.0.0.0 A-record response built and written back by hand; allowed queries are forwarded to a hardcoded upstream (8.8.8.8) over a socket exempted from the tunnel via `protect()` (required to avoid an infinite routing loop). **The IP/UDP/DNS packet parsing and construction in this file is hand-written byte manipulation with no test coverage and no ability to run it in this environment — it is the highest-risk file in the entire project.** Concretely to verify on real hardware before trusting it: DNS-over-UDP only (no DoT/DoH handling — a device configured to use DNS-over-HTTPS at the OS level would bypass this entirely, unlike the desktop, which explicitly firewalls known DoH resolver IPs; Android's per-app "Private DNS" setting is not addressed here), IPv4 only (no IPv6 fallback, which could leak blocked domains on an IPv6-preferring network), and no handling of multi-question DNS messages or EDNS0 (OPT) records beyond ignoring them.
- **Native-app blocking uses `AccessibilityService` + package-name-fragment matching**, not `killBackgroundProcesses` (explicitly disallowed by spec as unreliable) — matching on foreground-package + relaunching the shield activity on top, so a killed/backgrounded blocked app gains the user nothing since the very next foreground-window event re-shields it. The spec's documented fallback (`UsageStatsManager` polling for OEMs that deliver window-state events unreliably) is implemented as a callable method but is not wired to a periodic timer in this build — a reasonable, small follow-up, not done for time.
- **`killBackgroundProcesses` is never called anywhere in this codebase** — confirmed by design, not by grep, since the shield-relaunch approach was the only mechanism implemented.
- **The watchdog concept doesn't map onto Android.** A regular Android app cannot run a second always-alive background process the way the desktop's daemon+watchdog pair does — the OS actively prevents that. The closest real equivalents implemented here are: `START_STICKY` (ask the OS to restart the service if it's killed), `BOOT_COMPLETED` (restart at boot), and an `AlarmManager` heartbeat (`HeartbeatAlarmReceiver`, `setAndAllowWhileIdle` every 60s) that re-issues `startForegroundService` — a no-op if already running, a real restart otherwise. This is weaker than the desktop's ~2-second mutual-heartbeat guarantee: Doze mode and OEM battery managers (notoriously aggressive on some Chinese Android skins) can delay alarms well beyond 60s, and there is no way for a third-party app to fully defeat that without the user manually exempting it from battery optimization (requested during onboarding in `MainActivity`, but the user can decline or an OEM can silently re-restrict it later). Documented here rather than overclaimed.
- **Device admin is deactivated automatically on session completion** (`FocusLockDeviceAdminReceiver.deactivate()`, called from `FocusLockForegroundService.onSessionComplete`), matching spec — the app can only block its own uninstallation while a session is actually running, not permanently.
- **The Android "encrypted DataStore for session/ends_at" line in the spec's Android-specific section is not separately implemented.** The unified Data section's schema (sessions/settings/devices/active_session, identical shape to desktop) is implemented via plain Room/SQLite (`data/`), matching the spec's own cross-platform table description, but that SQLite file is not encrypted at rest. `androidx.security:security-crypto` is a declared dependency for this purpose but not yet wired into a `SQLCipher`-backed Room instance or an `EncryptedFile`. Given no session data here is more sensitive than "when did a focus session run and for how long," this was deprioritized in favor of getting every *enforcement* mechanism real, but it's a real, easy-to-close gap.
- Distribution is sideload-only by design (spec: Play rejects Accessibility Services used for blocking) — `./gradlew assembleDebug` is the intended artifact; no release-signing config was set up since there's no keystore or Play listing involved.

## Safety / anti-lockout

Built, not skipped, per the spec's explicit requirement:

- **8-hour hard cap**, enforced independently in three places so no single bug can bypass it: `shared/src/deadman.ts`'s `evaluateSessionRecord` (checked by the relay before accepting a `session.publish`, and by every client before accepting a remote session), `SessionManager.startSession` on desktop, and `SessionManager.startSession` on Android.
- **Dead-man's switch**: every client persists `ends_at` at session start (`active_session` table/row) and checks it against the current time on every startup, before doing anything else — `shared/src/deadman.ts`'s `shouldEnforceOnStartup` (desktop), the equivalent inline check in Android's `SessionManager.recoverOnStartup`. Verified by test on desktop (`session-manager.test.ts`'s three dead-man-switch tests: expired row → immediate full unblock, live row → resumed enforcement, no row → unblock).
- **Relay fail-open on start, fail-closed on stop**: a client that can't reach the relay simply doesn't get a new session propagated to it (fails open — no new block), but an already-running session ends locally on its own schedule regardless of relay reachability (fails closed on the thing that matters) — verified by `session-manager.test.ts`'s relay-disconnect test.
- **Never-block whitelist**: `desktop/src/daemon/enforcement.ts`'s `NEVER_BLOCK_DOMAINS` (localhost, OS update endpoints) is threaded through both the hosts-file writer and the process-kill matcher on both Windows and macOS enforcers, so it can't be bypassed by a category selection. Android's `blocklist/Blocklist.kt` has the equivalent `NEVER_BLOCK_DOMAINS` set, subtracted from the blocked-domain set before the VPN service ever null-routes anything. Phone-dialer/emergency-calling functionality was never touched by any code path in this project (the VPN only intercepts UDP/53 DNS traffic, never call signaling; the AccessibilityService only matches against the blocklist's own package-fragment list, which contains no dialer/phone packages).
- **Plain-text audit log**: `desktop/src/daemon/audit.ts` writes one newline-delimited JSON line per enforcement action (block applied/removed, hosts-file reversion, process kill, pairing events, session lifecycle) to `<app-data>/audit.log` — deliberately not SQLite, so it's readable even if the DB is corrupt. No Android equivalent was implemented (a real gap — Android's enforcement actions aren't separately audit-logged beyond what Logcat happens to capture, which isn't persisted).
- **Recovery documentation**: `README.md`'s Uninstall/Recovery section has the exact commands for Windows (tested reasoning, service names/rule names match `installer.nsh` exactly), macOS (written, unverified), and Android (`adb`).
